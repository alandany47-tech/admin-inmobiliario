# Sistema de Solicitudes de Pago y Tesorería - DIPZ Real Estate

## Stack Tecnológico
- **Framework:** Next.js (App Router, JS ES6+ puro, SIN TypeScript).
- **Base de Datos & Auth:** Supabase (`@supabase/supabase-js`, `@supabase/ssr`). Desde 0023 el sistema requiere login (Supabase Auth, `perfiles_usuario` con rol SOLICITANTE/APROBADOR/TESORERIA/ADMIN) — ver sección "Autenticación y Roles". El resto de las tablas de negocio (`solicitudes_pago`, `wbs_catalog`, etc.) **sigue con RLS abierto** (`for all using (true)`), es decir el login protege el acceso a la aplicación pero todavía no hay gating por rol a nivel de fila en esas tablas — pendiente como tarea aparte.
- **DB Connection:** Migraciones DDL vía `DATABASE_URL` en `.env.local`, aplicadas con `scripts/run-migration.js` (Node `pg`). Uso: `node scripts/run-migration.js supabase/migrations/000X_archivo.sql`.
- **Storage:** Bucket público `comprobantes` (comprobantes de pago).
- **UI & Iconos:** Tailwind CSS v4 (config CSS-first en `app/globals.css`, sin `tailwind.config.js`), `lucide-react`. Cero emojis en la interfaz. **Tema claro/oscuro:** `next-themes` (`ThemeProvider attribute="class"` en `app/layout.js`) + `@custom-variant dark (&:where(.dark, .dark *));` en `globals.css` para que las utilidades `dark:` respondan a la clase `.dark` en `<html>` en vez de `prefers-color-scheme` directamente (así el toggle manual del Navbar puede sobreescribir la preferencia del SO). Toggle Sol/Luna en `components/Navbar.js` vía `useTheme()`, con guardia de montaje para evitar mismatch de hidratación.
- **PDF/Excel:** `jspdf` + `html2canvas` (PDF con formato DIPZ y PDF masivo de tabla), `xlsx` (exportación a Excel).

## Esquema de Base de Datos (verificado en Supabase)
- `proyectos`: `id`, `codigo` (text, `UNIQUE` — constraint `proyectos_codigo_key`), `nombre` (text), `presupuesto` (numeric, presupuesto a nivel proyecto — no confundir con el presupuesto por partida de `wbs_catalog`), `created_at`. **RLS:** hasta 0015 solo tenía policy de `SELECT` (`"Permitir lectura publica"`) — a diferencia de todas las demás tablas (sin auth todavía) le faltaba la policy de escritura, así que crear/editar/eliminar proyectos fallaba con "new row violates row-level security policy" sin que hubiera ningún bug en la Server Action. 0015 la reemplazó por el patrón estándar `"anon acceso total proyectos"` (`for all using (true) with check (true)`). Desde 0021: `logo_proyecto_url` (text, nullable), `color_primario`/`color_secundario` (text, default `#0f172a`/`#2563eb`) y `estatus` (∈ En Desarrollo/Concluido/Archivado, default 'En Desarrollo') — branding para el logo dual (DIPZ + Proyecto) de los documentos y el filtro visual de `/proyectos`. `getProyectosStats()` (`app/actions/proyectos.js`) sigue viniendo de la RPC `get_proyectos_con_estadisticas()` (que no las expone) y les agrega estas 4 columnas en JS con un segundo `select` a `proyectos`, en vez de tocar la función de Postgres; `getProyectosBranding()` (mismo archivo) es un select directo de esas columnas, usado por el Cotizador.
- `proveedores`: `id`, `razon_social`, `rfc`, `datos_bancarios` (JSONB: `{banco, numero_cuenta}` si Banregio, `{banco, clabe}` si Otro), `estatus` ('Activo'|'Inactivo'), `contacto_nombre`, `contacto_telefono`, `contacto_email`, `created_at`.
- `cuentas_bancarias`: `id`, `nombre` (único; seed: "Caja Chica" y "Fresh Coco Desarrollos Banregio"), `tipo` ('Efectivo'|'Transferencia bancaria' — coincide con `metodo_pago`), `saldo_actual`, `saldo_inicial` (editable desde Tesorería; `actualizar_saldo_inicial_cuenta` traslada el delta a `saldo_actual` sin perder el efecto de movimientos previos), `created_at`.
- `movimientos_tesoreria`: bitácora de ingresos/egresos por cuenta. `id` (uuid), `cuenta_id`, `proyecto_id` (nullable), `tipo_movimiento` ('ingreso'|'egreso'), `fecha`, `razon_social`, `concepto`, `monto`, `saldo_resultante` (snapshot del saldo de la cuenta tras el movimiento), `comentarios`, `solicitud_id` (nullable, `on delete set null`; se llena automático cuando el movimiento viene de `procesar_pago_solicitud`), `created_at`. Los movimientos manuales se registran vía `registrar_movimiento_tesoreria`.
- `wbs_catalog`: `id`, `proyecto_id` (bigint NULL = catálogo general; FK a `proyectos.id`, que es bigint, no UUID), `categoria` (text), `partida` (text — ambas ampliadas de `varchar(100)` a `text` en 0009 porque WBS reales traen descripciones más largas), `presupuesto` (numeric, techo presupuestal de la partida, default 0), `activo` (boolean, default true — una partida con solicitudes `Pagado` asociadas nunca se puede renombrar ni desactivar, solo su presupuesto sigue editable), `codigo` (text NULL, ej. "1.1.01"; agregada en 0012, **la columna en sí sigue sin backfill** — el import por Excel todavía no la puebla), `parent_id` (bigint NULL, FK a `wbs_catalog.id` `on delete cascade`, agregada en 0012 para el árbol jerárquico de `/wbs`; hoy todas las filas existentes tienen `parent_id` NULL, por lo que el árbol se ve como lista plana hasta que algo la puebla), `created_at`.
  - **Formato de código a nivel de lectura (no de columna):** el catálogo real trae el código pegado como sufijo de `partida` (ej. `"Colado de Concreto (1.2.1)"`) en vez de en la columna `codigo` (que sigue NULL). `lib/wbs.js` (`normalizarPartidaWbs`) extrae ese sufijo `(\d+(\.\d+)+)` al final del texto y limpia `partida` **solo al leer**, en `getWbsCatalog`/`getWbsPresupuesto` (`app/actions/wbs.js`) — la fila en la base de datos no se modifica (excepto si alguien la renombra manualmente vía "Modo Edición" en `/wbs`, que sí persiste el texto ya limpio, dejando `codigo` todavía NULL). No asumir que `row.codigo` de un `select` directo a Supabase trae el valor mostrado en pantalla: solo lo trae si pasa por esas dos funciones.
- `folios_consecutivos`: `proyecto_id`, `periodo` (MMYY), `consecutivo` — solo la toca el trigger `generar_folio_solicitud`.
- `solicitudes_pago`:
  - `id`, `folio` (autogenerado por trigger: `[CODIGO_PROYECTO]-[MMYY]-[CONSECUTIVO]`, ej. `PIA-0826-001`).
  - `proyecto_id`, `proveedor_id`, `cuenta_id` (se llena solo al pagar).
  - `metodo_pago` ('Transferencia bancaria'|'Efectivo'), `solicitante`, `num_factura`, `wbs_categoria`, `wbs_partida` (texto libre, histórico — se dejan como están), `wbs_catalog_id` (bigint, FK a `wbs_catalog.id`; enlace fuerte hacia adelante, capturado al crear la solicitud desde el `id` del renglón WBS seleccionado; **no** se hizo backfill de solicitudes históricas, pendiente como tarea aparte).
  - `partidas` (JSONB array: `[{cantidad, descripcion, precio_unitario, subtotal}]`).
  - `concepto` (resumen autogenerado de las descripciones), `subtotal`, `aplica_iva` (boolean), `iva`, `total`.
  - `estado` ('Por Autorizar'|'Autorizado'|'Pospuesto'|'Pagado'|'Cancelado').
  - `fecha_programada` (se autocalcula al crear: próximo viernes), `fecha_pago` (se llena al pagar), `comprobante_url`.
- **Vista `wbs_presupuesto_resumen`:** por cada renglón de `wbs_catalog` expone `presupuesto`, `ejercido` (suma de `total` de solicitudes con `estado = 'Pagado'` ligadas por `wbs_catalog_id`), `disponible` (`presupuesto - ejercido`), `codigo` y `parent_id` (agregados en 0012 **al final** del `select`, no junto a `categoria`/`partida` — `create or replace view` no permite reordenar/insertar columnas en medio de una vista existente). Reescrita en 0016 (`wbs_jerarquia_y_resumen_recursivo.sql`) usando un CTE (`wbs_ejercido`) en vez de un único `select ... group by`, **sin cambiar columnas ni su orden** — un borrador previo de esa migración sí las reordenaba (`codigo`/`parent_id` junto a `categoria`/`partida`) y se descartó esa parte porque `create or replace view` la habría rechazado (mismo gotcha que 0012). El `ejercido` que expone la vista sigue siendo el de la propia fila, **no** un agregado sobre el subárbol: la consolidación jerárquica de presupuesto/ejercido/disponible de un nodo padre sobre todos sus descendientes se calcula en el cliente (`construirArbol` en `components/PanelPresupuestoWbs.js`), no hay CTE recursiva de árbol en la vista. Fuente de verdad para la vista `/wbs` y para `getWbsCatalog` (usado también por el combobox WBS de `SolicitudPagoForm`); el árbol se arma en el cliente a partir de `parent_id`, agrupado por `categoria` como nivel superior.
- **Funciones Postgres:**
  - `generar_folio_solicitud()` (trigger BEFORE INSERT).
  - `procesar_pago_solicitud(p_solicitud_id, p_fecha_pago)` (RPC atómica): valida que la solicitud esté 'Autorizado', determina la cuenta por `tipo = metodo_pago`, descuenta `saldo_actual`, marca `estado = 'Pagado'` **y además inserta el egreso correspondiente en `movimientos_tesoreria`**. Trae un bloque de validación de presupuesto por partida WBS (compara `total` contra `wbs_presupuesto_resumen.disponible`) que está **comentado/desactivado a propósito** — descomentar en una migración nueva cuando se quiera bloquear pagos que exceden presupuesto. Cualquier cambio a estado 'Pagado' debe pasar por esta función, nunca por un `update` directo del estado.
  - `actualizar_saldo_inicial_cuenta(p_cuenta_id, p_saldo_inicial)`: ajusta `saldo_inicial` y traslada el mismo delta a `saldo_actual`.
  - `registrar_movimiento_tesoreria(...)`: inserta un movimiento manual (ingreso/egreso) en la bitácora y actualiza `saldo_actual` de forma atómica.
  - `revertir_pago_solicitud(p_solicitud_id, p_nuevo_estado default 'Por Autorizar')` (RPC atómica; default cambiado de 'Autorizado' a 'Por Autorizar' en 0013 — el resto de la lógica es idéntica a 0011): valida que la solicitud esté 'Pagado', restaura `saldo_actual` de la cuenta asociada, inserta un `ingreso` de compensación en `movimientos_tesoreria` (referenciando la misma `solicitud_id`, nunca borra el egreso original) y regresa la solicitud a `p_nuevo_estado` (`fecha_pago` y `cuenta_id` a `null`). Cualquier cambio de estado que salga de 'Pagado' debe pasar por esta función, nunca por un `update` directo. Hoy solo se invoca sin `p_nuevo_estado` (usa el default) desde `revertirPagoSolicitud` en `app/actions/tesoreria.js` — Control Maestro ya no tiene botón de reversión (ver sección de Control Maestro).
  - `editar_movimiento_tesoreria(p_movimiento_id, p_nuevo_monto)` (RPC atómica, 0012): recalcula el delta entre el monto anterior y el nuevo, lo traslada a `cuentas_bancarias.saldo_actual` (signo según `tipo_movimiento`) y actualiza `monto`/`saldo_resultante` del propio renglón. Si el movimiento tiene `solicitud_id`, también sincroniza `solicitudes_pago.total = p_nuevo_monto` (para no desfasar `wbs_presupuesto_resumen.ejercido`) **sin distinguir** si es el egreso original o el ingreso de compensación de una reversión — editar ese segundo caso es un uso de borde no contemplado. No recalcula el `saldo_resultante` de movimientos posteriores en la bitácora (queda como snapshot histórico); solo `saldo_actual` es siempre el balance vigente.
  - `eliminar_movimiento_tesoreria(p_movimiento_id)` (RPC atómica, 0012): revierte el efecto del movimiento en `saldo_actual`, y si tenía `solicitud_id` con estado todavía 'Pagado' la regresa a 'Autorizado' (`fecha_pago`/`cuenta_id` a `null`) antes de borrar el renglón. **No** delega en `revertir_pago_solicitud` — esa función inserta un movimiento de compensación nuevo, lo que aquí duplicaría el efecto porque el renglón que se borra ya es, en sí mismo, la reversión.
  - `get_desglose_pagos_wbs(p_wbs_id)` (RPC de solo lectura, 0014): `WITH RECURSIVE` sobre `wbs_catalog.parent_id` desde `p_wbs_id` hacia sus descendientes, y regresa todas las `solicitudes_pago` con `estado = 'Pagado'` ligadas a cualquiera de esos nodos (`solicitud_id, folio, proyecto_nombre, proveedor_razon_social, concepto, fecha_pago, metodo_pago, monto, comprobante_url`). Funciona tanto sobre un nodo hoja como sobre uno con hijos (agrega todo el subárbol), por eso en `/wbs` la celda "Ejercido" es clicable en cualquier nivel del árbol.
  - `get_proyectos_con_estadisticas()` (RPC de solo lectura, 0015): por cada `proyecto` regresa `presupuesto`, `total_pagado` (suma de `total` de `solicitudes_pago` en `estado = 'Pagado'` ligadas por `proyecto_id`) y `total_partidas_wbs` (conteo de filas de `wbs_catalog` con ese `proyecto_id`, hoja o no). Fuente de `getProyectosStats()` en `app/actions/proyectos.js`, usada en `/proyectos`.
  - **Cuidado al modificar `procesar_pago_solicitud`:** ya se pisó por accidente una vez (0008 la redefinió a partir de una versión vieja sin la bitácora que 0006 ya había agregado, corregido en 0010). Antes de hacer `create or replace function` sobre esta función, releer su definición actual en la BD (`pg_get_functiondef`), no asumir el contenido del último archivo de migración que la tocó.
- `wbs_historial_cambios` (0018): `id` (uuid), `wbs_catalog_id` (FK a `wbs_catalog.id` `on delete cascade`), `presupuesto_anterior`, `presupuesto_nuevo`, `orden_cambio_ref` (nullable, sin UI dedicada todavía), `comentario` (not null), `created_at`. Una fila por cada cambio de presupuesto confirmado desde `/wbs` (no aplica a renombres); `actualizarPresupuestoWbs` (`app/actions/wbs.js`) ahora exige un tercer parámetro `comentario` y la inserta después del `update` a `wbs_catalog`.
- **Módulo de Cobranza y Selección de Unidades** (0019, esquema ampliado en 0020 y 0021): `clientes` (`id` uuid, `nombre`, `rfc`/`telefono`/`email` nullable, y desde 0020 `direccion`/`contacto_secundario`/`notas` nullable), `unidades` (`id` uuid, `proyecto_id` bigint FK, `codigo_unidad` único por proyecto, `superficie_m2`, `monto_lista`, `estatus` ∈ SIN ASIGNAR/APARTADA/VENDIDA — **en mayúsculas desde 0020**, reemplaza a Disponible/Apartada/Vendida; `precio_m2` (numeric, default 0, agregada en 0020, `monto_lista = superficie_m2 * precio_m2` se mantiene en el cliente, ver `PanelUnidades.js`), `tipo_uso` ∈ DEPARTAMENTO/OFICINA/LOCAL/BODEGA/OTRO (agregada en 0020, **reemplaza** a la columna `tipo_unidad` ∈ CLIENTE/INVERSIONISTA/SIN ASIGNAR de 0019, eliminada en la misma migración — "SIN ASIGNAR" pasó de ser un valor de `tipo_unidad` a ser el estatus de disponibilidad) y desde 0021 `esquema_unidad` ∈ TRADICIONAL/INVERSIONISTA (default TRADICIONAL, badge morado en `PanelUnidades.js`; **solo distintivo visual/informativo** — no cambia la lógica de generación del plan de pagos)), `contratos_venta` (`id` uuid, liga `proyecto_id`+`unidad_id`+`cliente_id`, `monto_total_venta`, `fecha_contrato`, `estatus` ∈ Activo/Finiquitado/Cancelado — desde 0021 también `Cancelado` se usa para el caso de separación vencida sin liquidar, ver `liberarUnidadVencida`), `planes_pago_cobranza` (`id` uuid, `contrato_id` FK `on delete cascade`, `tipo_pago` ∈ ENGANCHE/MENSUALIDAD/A ENTREGA/SEPARACION, `monto_programado`, `monto_pagado`, `fecha_programada`, `fecha_pago`, `estatus` ∈ Pendiente/Pagado/Vencido/Parcial — nada pone `Vencido` automáticamente, es un estatus manual/futuro; el vencimiento visual hoy se calcula en cliente/vista comparando `fecha_programada` contra hoy sobre filas Pendiente/Parcial —, `cuenta_id`, `movimiento_tesoreria_id`, `folio_recibo`, `notas`). Las 4 tablas usan `uuid` como PK (no `bigint identity` como el resto del esquema, sigue el mismo patrón que `movimientos_tesoreria`). `movimientos_tesoreria` gana la columna `plan_pago_cobranza_id` (uuid, nullable, `on delete set null`) — simétrica a `solicitud_id` para trazabilidad, pero **`editar_movimiento_tesoreria`/`eliminar_movimiento_tesoreria` no la conocen**: solo saben sincronizar `solicitudes_pago` vía `solicitud_id`, así que editar/eliminar desde Tesorería un ingreso que vino de Cobranza ajusta el saldo de la cuenta pero puede desfasar `planes_pago_cobranza.monto_pagado/estatus`. **A diferencia de Solicitudes de Pago, Cobranza no tiene un `revertir_pago_cobranza` equivalente a `revertir_pago_solicitud`** — revertir un abono o cancelar un contrato con pagos ya dispersados hoy requiere corregir el saldo de la cuenta a mano desde Tesorería; queda pendiente como tarea aparte (limitación conocida, no resuelta en 0019/0020/0021).
  - **Ciclo de vida de venta (0021): Separación (30 días) → Liquidación de Enganche + Firma → Vendida.** `contratos_venta` gana `fecha_separacion` (timestamptz, default now()), `fecha_limite_apartado` (timestamptz, default now()+30 días), `monto_separacion`, `monto_enganche_pactado`, `monto_enganche_pagado` (numeric, default 0 — el segundo se sincroniza en JS desde `procesarPagoCobranza` sumando `monto_pagado` de las filas `tipo_pago='ENGANCHE'` del contrato tras cada abono, **no** dentro del RPC de dinero, por la regla 7), `contrato_firmado` (boolean, default false), `dia_pago_mensual` (int NULL, 1–31, se define solo al confirmar firma) y `esquema_venta` ∈ TRADICIONAL/INVERSIONISTA (se copia del `esquema_unidad` al apartar, editable). `planes_pago_cobranza` gana `fase_plan` ∈ PROYECTADO/ACTIVO (default PROYECTADO): mientras el contrato no está firmado, todas sus filas (separación/enganche/mensualidades/entrega) son supuestos en fase PROYECTADO — **siguen siendo pagables** (Captura de Pagos no filtra por fase para permitir abonar), pero no alimentan las alertas de vencimiento ni cuentan en `vista_cartera_clientes.mensualidades_activas`; al confirmar la firma, `confirmarFirmaContrato` las pasa todas a ACTIVO de un solo `update`.
    - `crearSeparacionUnidad(payload)` (`app/actions/cobranza.js`, reemplaza a `crearContratoVenta`): crea el contrato con `contrato_firmado=false`, inserta la fila `SEPARACION` del plan, y marca la unidad `APARTADA` (**no** `VENDIDA`).
    - `confirmarFirmaContrato(contratoId, diaPagoMensual)`: valida `monto_enganche_pagado >= monto_enganche_pactado` y que no esté ya firmado; si pasa, marca `contrato_firmado=true`, guarda `dia_pago_mensual`, activa todo el plan (`fase_plan='ACTIVO'`) y marca la unidad `VENDIDA`. Se invoca desde el botón "Confirmar Firma de Contrato y Activar Calendario" en `CapturaPagos.js` (visible solo cuando el enganche ya se liquidó por completo; el avance se deriva del `plan` cargado en el cliente, no de `contrato.monto_enganche_pagado`, para no quedar desfasado entre abonos sin recargar el contrato).
    - `liberarUnidadVencida(unidadId)` (`app/actions/unidades.js`): si la unidad está `APARTADA`, su contrato `Activo` no está firmado y `fecha_limite_apartado` ya pasó, cancela el contrato (`estatus='Cancelado'`, no se borra) y regresa la unidad a `SIN ASIGNAR`. Botón "Liberar Unidad (Separación Vencida)" en el modal de detalle de `PanelUnidades.js`, junto con el contador de días restantes (o "Vencida") que también se muestra en la tarjeta de la unidad.
    - `ModalWizardSeparacion.js` (reemplaza a `ModalAsignarUnidad.js`, eliminado): wizard único de 4 pasos condicionales (unidad → cliente → separación → plan proyectado) usado tanto desde `PanelUnidades.js` (con `unidadPreset` fijo, salta el paso de unidad) como desde `CarteraClientes.js` (con `clientePreset` fijo, salta el paso de cliente) — toda alta de venta pasa por el mismo ciclo Separación→Firma sin importar desde dónde se inicia.
  - `procesar_pago_cobranza(p_plan_pago_id, p_cuenta_id, p_monto, p_fecha_pago, p_metodo_pago)` (RPC atómica, 0019, sin cambios en 0021): mismo patrón que `procesar_pago_solicitud` (`FOR UPDATE` en el plan y la cuenta, inserta el ingreso en `movimientos_tesoreria`, actualiza `saldo_actual` y el `monto_pagado`/`estatus`/`fecha_pago`/`cuenta_id`/`movimiento_tesoreria_id` de la fila del plan). Invocada por `procesarPagoCobranza` en `app/actions/cobranza.js`, que además sincroniza `contratos_venta.monto_enganche_pagado` (ver arriba).
  - `revertir_pago_cobranza(p_plan_pago_id)` (RPC atómica, 0022): equivalente a `revertir_pago_solicitud` pero para Cobranza — antes de esta migración, deshacer un abono mal capturado requería 3 pasos manuales desde Tesorería (ajustar saldo, borrar/editar el movimiento, corregir a mano `monto_pagado`/`estatus` del plan), con alto riesgo de dejar saldo o plan desfasados. Valida `monto_pagado > 0` y `cuenta_id` no nulo, descuenta **`monto_pagado` completo** (no solo el monto del último movimiento) de `saldo_actual` en `cuenta_id`, inserta un `egreso` de compensación en `movimientos_tesoreria` (mismo `plan_pago_cobranza_id`, nunca borra los ingresos originales) y regresa la fila a `monto_pagado=0`/`estatus='Pendiente'`/`fecha_pago`/`cuenta_id`/`movimiento_tesoreria_id` a `null` — reversión **total** de la fila (como `revertir_pago_solicitud`), no de un abono parcial específico. Por qué `monto_pagado` y no el monto del `movimiento_tesoreria_id` ligado: una fila de `planes_pago_cobranza` puede recibir varios abonos parciales y `procesar_pago_cobranza` sobrescribe `movimiento_tesoreria_id` con el del último abono en cada llamada, así que ese FK por sí solo no basta para saber cuánto entró en total. **Caso de borde sin resolver:** si los abonos parciales de una misma fila se hicieron a cuentas bancarias distintas, la reversión completa se aplica solo a la última `cuenta_id` conocida, no se reparte entre las cuentas originales. Invocada por `revertirPagoCobranza` en `app/actions/cobranza.js`, que además — igual que `procesarPagoCobranza` — resincroniza `contratos_venta.monto_enganche_pagado` si la fila revertida es `tipo_pago='ENGANCHE'` (extraído a un helper compartido `sincronizarEnganchePagado`, fuera del RPC de dinero por la regla 7). **Caso de borde documentado, no automatizado:** si la fila revertida era la que completaba el enganche de un contrato ya `contrato_firmado=true` (unidad ya `VENDIDA`), la función no revierte automáticamente la firma ni el estatus de la unidad — solo deja `monto_enganche_pagado` por debajo de `monto_enganche_pactado`; decidir qué hacer con una unidad ya vendida cuyo enganche se "desliquida" es una decisión de negocio pendiente, no un bug.

## Reparto de Gastos Corporativos, Firmas de Autorización y Logo de Empresa (0027-0029)

## Reglas de Desarrollo & Optimización de Tokens
1. **Atomicidad:** Generar cambios modulares por archivo. No refactorizar código que no se solicitó modificar.
2. **Concisión:** Respuestas en CLI limitadas al estado de ejecución y lista de archivos modificados. Cero explicaciones redundantes.
3. **Estilo:** JavaScript ES6+ directo, Tailwind nativo, JSDoc mínimos solo en Server Actions/componentes exportados. Cero emojis.
4. **Clientes Supabase:** Usar siempre `lib/supabase/server.js` para Server Actions/Components y `lib/supabase/client.js` para Client Components.
5. **Migraciones:** Todo cambio de esquema va en un nuevo archivo numerado en `supabase/migrations/` (siguiente consecutivo libre) y se aplica con `scripts/run-migration.js`, nunca a mano fuera de ese flujo.
6. **Dinero:** Cualquier movimiento que afecte `cuentas_bancarias.saldo_actual` debe pasar por una función Postgres atómica (patrón `procesar_pago_solicitud`), no por updates sueltos desde Server Actions.
7. **`create or replace function` sobre funciones compartidas:** antes de redefinir una función Postgres que ya existe (ej. `procesar_pago_solicitud`), releer su definición actual en la base (`select pg_get_functiondef(oid) from pg_proc where proname = '...'`) en vez de asumir que el archivo de migración más reciente que la mencionó es su versión vigente — otra migración posterior pudo haberla vuelto a redefinir.
8. **Tema claro/oscuro:** usar siempre utilidades `dark:` de Tailwind; la estrategia es por clase (`@custom-variant dark` en `globals.css` + `next-themes`), no por `prefers-color-scheme` directo — no agregar `@media (prefers-color-scheme: dark)` a mano, se ignoraría el toggle manual del Navbar.
9. **Layout de páginas:** los contenedores `<main>` de cada página usan `max-w-7xl mx-auto px-4` (no `max-w-4xl`/`5xl`/`6xl` sueltos) para mantener el ancho consistente entre vistas.
10. **RLS de tablas nuevas:** toda tabla sin auth debe traer una policy `for all using (true) with check (true)` (patrón `"anon acceso total <tabla>"`), no solo una de `SELECT` — `proyectos` se creó con solo una policy de lectura y bloqueó su propio módulo CRUD (`app/actions/proyectos.js`) hasta 0015, con un error de RLS en vez de un bug obvio en el código. Antes de asumir que una tabla ya tiene acceso de escritura, revisar `pg_policy`.
11. **`react-hooks/set-state-in-effect` (regla de ESLint, `eslint-config-next`):** nunca llamar a un setter de estado de forma síncrona en el cuerpo de un `useEffect` (sí está permitido dentro de un callback async/`.then`, ahí no se marca). Dos patrones ya usados en el código para el caso típico de "resetear estado al cambiar de proyecto/id" (`PanelUnidades.js`, `PanelPresupuestoWbs.js`, `SolicitudPagoForm.js`): mover el reset al handler `onChange` del selector en vez de a un `if (!id) { setX(...); return; }` al inicio del efecto, y para el flag de "cargando" inicializarlo con `useState(Boolean(id))` en vez de `setCargando(true)` al inicio del efecto. Para modales que cargan datos al abrirse con un id que cambia (`ModalVisorPDF.js`, `ModalDesglosePagosCliente.js`, `ModalDesglosePagosWbs.js`): ajustar el estado durante el render comparando el id contra uno guardado en state (`if (open && id !== idEnCurso) { setIdEnCurso(id); setCargando(true); ... }`, patrón "Adjusting state when a prop changes" de la documentación de React) en vez de dentro del efecto. `Navbar.js` es la única excepción real (el flag de montaje para evitar mismatch de hidratación no tiene forma de moverse fuera del efecto) y lleva `// eslint-disable-next-line react-hooks/set-state-in-effect` explícito.

- **Análisis de impacto antes de tocar algo compartido**: antes de renombrar, mover, borrar o cambiar la firma de una función, tabla, columna o módulo usado en más de un lugar (ej. `procesar_pago_solicitud`, `wbs_catalog`, `normalizarPartidaWbs`, cualquier Server Action en `app/actions/`), correr `graphify explain "<símbolo>"` o `graphify path "<símbolo>" "<archivo que lo llama>"` para ver todo lo que depende de él antes de editar. El objetivo es detectar qué se puede romper en otro archivo antes de hacer el cambio, no después.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost). Git hooks (`graphify hook install`) automatizan esto en cada commit/checkout; si no están instalados, correr `graphify update .` a mano tras cambios grandes.
